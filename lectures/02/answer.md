     - **① 用語集にある語（そのままの質問）**：「LoRAとは何ですか？」「量子化とは何ですか？」（正解：`needs_review: false`＋用語集の定義）
     - **② 言い回しを変えた質問**：「重みを固定して低ランク行列だけを学習する手法は？」「LoRAの仕組みを簡単に教えてください」（正解：`needs_review: false`＋対応する定義）

- 結果：
  - **学習前**：`format_rate` が低く、`needs_review` キーの欠落が多発した。また、③の用語集にない語（FlashAttention等）に対しても、ベースモデルの事前学習知識を使ってそのまま説明してしまい、「用語集にないため確認が必要（`needs_review: true`）」という振る舞いができなかった。
  - **学習後**：
    - **出力形式**：全問で厳密なJSON形式（`{"answer": ..., "needs_review": ...}`）を守れるようになった（`format_rate = 1.0`）。
    - **① 用語集にある語・② 言い回しを変えた質問**：定型的な質問には用語集通りの定義を返せるようになった一方、言い回しを大きく変えた質問では、小規模モデル（0.8B）への少数ステップのSFTだけでは知識の汎化が不十分で、別の用語の定義を混ぜたり断定を誤るケースが見られた。
    - **③ 用語集にない語**：「記載がありません」と返せる割合は増えたものの、学習データ内の単語と表層的に似た未知語に対しては、既存の定義を無理やり当てはめて `needs_review: false` と断定してしまうハルシネーションが一部残った。
- 気づき・疑問（用語集を検索する仕組み［RAG / Agent Tool］と比較した、モデルを学習させる際のメリット・デメリット）：
  - **モデルを学習させる（SFT / LoRA）メリット**：
    1. **出力フォーマットや応答スタイルの強制力**：厳密なJSONスキーマや `needs_review` フラグの付与ルール、文体の統一など、「どう答えるか（How）」の振る舞いを少ないプロンプトトークンで安定して定着させられる。
    2. **推論時のコンテキスト節約・低レイテンシ**：毎回プロンプトに用語集データや検索結果を注入する必要がないため、1回あたりの入力トークン数を抑えられ、ツール呼び出しの往復（複数リクエスト）も発生しない。
  - **モデルを学習させる（SFT / LoRA）デメリット（検索する仕組みの優位性）**：
    1. **知識の更新コストと鮮度**：用語集に新しい用語が1つ追加・修正されるたびに再学習（ファインチューニング）が必要になる。一方、検索する仕組み（RAGや第3回の `search_glossary` ツール）なら `glossary.json` を書き換えるだけで即座に最新知識を反映できる。
    2. **事実の正確性と「知らないこと」の境界判定（Grounding）**：SFTで重みに知識を焼き込むアプローチでは、0.8Bのような小規模モデルに正確な事実を暗記させるのが難しく、未知の用語に対するハルシネーション（無理な当てはめ）を完全に防げない。対して検索アプローチでは、検索結果が0件（空リスト）であれば決定論的に「用語集にない」と判定できるため、事実性と根拠の有無の判定においては検索（RAG/Tool）の方が圧倒的に信頼性が高い。
    3. **結論としての使い分け**：「ドメイン固有の事実知識の参照・有無判定」は検索（RAG/ツール）に任せ、「出力形式（JSON）の遵守やトーン＆マナーの制御」にSFTを使うというハイブリッドな役割分担がエンジニアリング上もっとも有効であると考察した。
